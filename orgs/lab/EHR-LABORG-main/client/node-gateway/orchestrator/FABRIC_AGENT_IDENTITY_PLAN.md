## 4. Current Gateway Identity Flow

The Express API Gateway (`client/node-gateway/server.js`) uses `client/node-gateway/gateway.js` to connect to Fabric via the gRPC `@hyperledger/fabric-gateway` SDK.

1. **Identity Reading (`newIdentity()`)**:
   - Reads X.509 certificate from: `organizations/peerOrganizations/lab.example.com/users/User1@lab.example.com/msp/signcerts/User1@lab.example.com-cert.pem`.
   - Binds `mspId: 'LabMSP'`.
2. **Signer Reading (`newSigner()`)**:
   - Reads private key from: `organizations/peerOrganizations/lab.example.com/users/User1@lab.example.com/msp/keystore/` (reads first file).
   - Constructs private key signer using Node `crypto` + Fabric `signers.newPrivateKeySigner(privateKey)`.
3. **gRPC Connection (`newGrpcConnection()`)**:
   - Loads connection profile from `connection-profiles/lab-connection.json`.
   - Resolves peer target (`peer0.lab.example.com:7051` or `GATEWAY_PEER` env var).
   - Reads TLS root CA cert from `peer.tlsCACerts.pem`.
   - Establishes gRPC Client with `grpc.credentials.createSsl(tlsRootCert)` and override target `peer0.lab.example.com`.

## 9. Step-by-Step Implementation Plan

### Step 1: Update `crypto-config.yaml` to Include Agent Identity
Modify `config/crypto-config.yaml` to specify dedicated user identities under `PeerOrgs.Lab`:

```yaml
PeerOrgs:
  - Name: Lab
    Domain: lab.example.com
    EnableNodeOUs: true
    Template:
      Count: 3
    Users:
      Count: 2  # User1@lab.example.com (User 1) and labagent@lab.example.com (User 2)
```

### Step 2: Regenerate Crypto Material
Run `cryptogen extend` or `cryptogen generate` to create the `labagent` user credentials under:
`organizations/peerOrganizations/lab.example.com/users/labagent@lab.example.com/msp/`

### Step 3: Configure Agent Identity Path in `gateway.js`
Update `gateway.js` (or `tools/fabric-tools.js`) to support an environment variable `FABRIC_USER`:
```javascript
const user = process.env.FABRIC_USER || 'User1@lab.example.com';
const USER_MSP_DIR = path.join(
  ROOT_DIR,
  'organizations',
  'peerOrganizations',
  'lab.example.com',
  'users',
  user,
  'msp'
);
```

### Step 4: Containerize Agent Node (Phase 2)
In Phase 2, mount `labagent` MSP directory into the dedicated `lab-agent` container read-only:
`- ../organizations/peerOrganizations/lab.example.com/users/labagent@lab.example.com/msp:/app/msp:ro`

## 13. Security Considerations

1. **Attribution**: Every transaction initiated by the AI agent will show `labagent@lab.example.com` in the transaction creator header, establishing explicit auditability.
2. **Independent Revocation**: If the AI agent is compromised, `labagent@lab.example.com` certificate can be revoked via CRL without affecting human user `User1@lab.example.com`.
3. **Read-Only Volume Mounts**: Private keys are mounted into agent containers read-only (`:ro`).
4. **Least Privilege**: In Phase 2, chaincode can enforce ABAC rules checking `role=aiagent` attribute on transaction creator certs.

---

## 14. Rollback Plan

If switching to `labagent` identity encounters any gRPC or TLS issues:
1. Set `FABRIC_USER=User1@lab.example.com` in environment variables.
2. Gateway immediately falls back to existing working `User1` credentials.
3. Zero downtime or network rebuild required.
